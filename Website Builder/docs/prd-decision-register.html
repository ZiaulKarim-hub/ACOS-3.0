01The product, in eight steps

A Claude Code skill that turns a conversation into a distinctive, hand-adjustable website. You are the aesthetic judge at every step. There is no AI critic scoring screenshots in a loop — that architecture was explicitly replaced.

StepWhat happensWho does it
0Warm start — reuse a prior design system or site if one exists, plus asset-library detectionskill
1Interview: purpose, audience, positioning, taste, accessibility, performance, constraints. 78-question bank, three tiers, ~35–45 answeredskill
2Write a prompt that produces the whole design system — typography, colour, motion, artwork, componentsskill
3Paste that prompt into claude.ai on the web, generate, hand-carry the result backyou, by hand
4Interview again to select components, then build the site as a live editable design surfaceboth
5If nothing looks good: more variants, a scoped section regeneration, or a brand-new system promptyou

Step 3 is the pipeline's weak point and the PRD says so. The manual hand-carry is named as the single biggest threat to the tool being used more than twice. A zero-paste alternative — Local Regeneration Mode — ships in v1 alongside it, as a first-class path rather than a fallback of last resort.

02Locked decisions

Five decisions you made in conversation. Each is recorded as settled and marked do not reopen — a later session may implement them but may not re-litigate them. You can of course overturn any of them; nobody else can.

D1 Coherent design directions, not independent per-item picks Settled 2026-07-25

About 10 complete, internally consistent design directions, each covering the identity-carrying items — font pairing, colour scheme, button, cursor, background, ribbon, hero animation. 20 artworks, tagged by which directions they suit. Within your chosen direction, 10 variants of each swappable component, generated on demand rather than all upfront. Derived values — spacing, radius, shadow scales — are computed from the direction, never picked independently.

Why. Applied literally, "10 variants of each item" meant roughly 800 artifacts through a manual paste boundary. Worse, independent picks clash: button variant 3, ribbon variant 7 and cursor variant 9 need not belong to the same visual world. Your 10 and your 20 are preserved — they arrive as coherent sets rather than a pile.

Rejected: literal independent per-item variants. Rejected on coherence and volume grounds, not because the instinct was wrong — 10 options per identity item is the right amount of choice; the fix was to bundle them.

memory/decisions/D1-design-directions-not-independent-picks.md · §7, §8

D2 Constraint-based dragging, with a free-position escape hatch Settled 2026-07-25

Every component is pinned or anchored — left, centre, stretch, relative to a parent or to the element above — so layout reflows on smaller screens. An explicit per-component free-position escape hatch exists for cases that need it. Gridlines are what components snap to: the layout substrate, not decoration that gets hidden later.

Why. Free x/y dragging fights responsive layout. A site must work at 390px and 1440px. If a headline is dragged 40px left on the large screen, nothing in the brief says what happens on the phone. The alternative — arranging the page separately per screen size — is roughly three times the work.

Live risk R47: there is no way to validate a constraint drag model without building one. Its day-to-day usability is unvalidated at first ship, and the stated mitigation is explicitly marked partial.

memory/decisions/D2-constraint-based-dragging.md · §11

D3 LOCK exports clean code; it does not hide a toolbar Settled 2026-07-25

LOCK exports. It produces a clean static site with no editor runtime shipped to visitors, while the editable project stays beside it so design mode can be re-entered. Five purity gates. Re-render, not copy-strip — the clean build is generated afresh rather than produced by deleting things.

Why. Read naively, "removed" could mean hidden. If LOCK only hid the editor, the finished site would still ship the entire editing engine to every visitor — slow, and it makes "the site as a visitor sees it" a lie.

Unresolved proof. Purity was specified as two-build byte-equality. No source consulted established that Astro/Vite builds are byte-reproducible across two installs. A Phase-0 spike is required, with a normalised-comparison fallback that explicitly weakens D3's proof. See decision 5.

memory/decisions/D3-lock-exports-clean-code.md · §12.5, §12.8

D4 Motion is a design-system item, living in draggable art containers Settled 2026-07-26

Animation is an ordinary design-system item with variants — same generate-then-pick flow as fonts, buttons and cursors. Animated pieces live in the same draggable containers as artwork; the editor manipulates an animated container exactly as it manipulates a JPEG. Motion is not a separate parallel subsystem.

Every container carries a reduced-motion variant reference — an art-directed alternative, not a switch that turns motion off — and a pause affordance reference, so an unpausable marquee is structurally unbuildable.

Rejected: a separate motion verification channel (filmstrip capture, interaction-manifest walking) as a parallel v1 subsystem. Deferred rather than adopted.

Carried caveat: motion remains the weakest thing to verify and the strongest thing award juries reward. Folding it into the system does not solve that.

D5 Layers are a real document tier, and editing one never disturbs the layers below Settled 2026-08-20

Offered an authoring-order rule or a structural split, you chose the structural split, and set the governing requirement with it: work on separate layers without changing the bottom layer or layers.

The layout contract goes from four levels to five. A layer is a depth axis, not a containment one, so it does not append as a fifth level — it splits the old level 2. Page is a vertical list of sections plus at most one optional page backdrop layer. Section is an ordered stack of layers. Layer is the real CSS Grid, and every layer in a section shares that section's track definition without exception. Block is integer grid placement on exactly one layer. Inside a block is flow only.

Sections own the stacks; the page backdrop carries no content. This is derived, not preferred: level 1 is reorder-only, so page-wide content layers would let a section reorder slide its blocks out from under the artwork they were composed against. The page backdrop exists for one continuous wash behind the whole page, and is art and motion only.

Isolation is enforced structurally, not by convention. Exactly one layer is active; the others render but are inert. Underneath that, layer-scoped writes: every op the editor emits carries a layerId, and an op whose target node's layerId differs is rejected, not applied. That turns "without changing the bottom layers" into an assertable invariant over the op log rather than a promise.

It closes an existing trap. §7.5 warns that a transformed art container silently swallows every dropdown inside it — the user sees "the menu is behind the picture" with no visible cause. A stack of independently animatable layers would make that worse, so overlay-class content (dropdown 200, overlay 300, modal 400, popover, skipLink) now renders into a page-level overlay root outside the layer stack. The trap becomes impossible rather than lint-detectable.

Your build-order request survives as a consequence. Step 4 gains a layer-ordered build: a section's bottom layer is composed and approved before work moves up. You get the ordering and the structure, not one instead of the other.

Rejected: the authoring-order-only reading; page-owned layer stacks carrying blocks; and a layer-count cap — the cost that matters is GPU and main-thread load from placed instances, which §9.5's costClass validator already caps where it occurs.

04The four sign-off rows

Section 18's deviations table. Each row is a place where v1 as drafted does less than the eight-step brief promised. §18 calls these deviations from a settled brief, not sequencing details, and blocks all v1 work until they are resolved.

4(c) Inline text formatting is v2 Needs your ruling

What v1 gives you. Click any heading, eyebrow, button, nav item, label or stat number and type. The mechanism is contenteditable="plaintext-only" — a browser mode that allows in-place editing but refuses all formatting and strips pasted markup. It covers about 90% of a marketing page's text nodes.

What it does not give you. Inside a paragraph of body copy: no bold, no italic, no list, and no link on a phrase. The real editor for that — TipTap / ProseMirror, MIT-licensed, restricted to bold, italic, link, list, blockquote with no font, colour or size controls — is v2.

The consequence. The gap lands on exactly two components: Rich text / prose body and Legal / policy body. A privacy policy with no clickable links, and body copy that cannot link anywhere, is a hole a user hits on day one.

Cost honesty. "Just add links" is not cheap. plaintext-only refuses markup by design, so a link means installing the real editor anyway. You would be buying the whole rich-text block and choosing to show fewer buttons on it.

  • Accept. No inline formatting or links in v1 body copy.
  • Pull the rich-text block into v1, restricted mark set, long-form prose blocks only.
RecommendationB. A body-copy system that cannot hold one link is not finished. The cost is not in §18's day estimate, so this grows the schedule again on top of Decision 1.

  • Generate two full directions in v1.
RecommendationA, strongly. Beyond the cost, cross-direction swapping arguably fights D1's own logic: if a direction is a coherent whole, pulling one card out of a different one breaks the thing D1 exists to protect.

NEW-2 An engine that generates animations in a customizable way Extends D4 — needs a ruling

What exists today

The motion model is pick-from-a-catalogue, with two composable axes. §9.1.1 defines them:

  • variant — the container's structural build and skin, drawn from §9.2's per-kind count.
  • props.motion — the choreography, a token shaped <kind>.<slug>@<version> drawn from §9.3's animation kinds. Combined with trigger (a closed list: page-load, viewport-enter, viewport-scrub, pointerenter, click, always) it decides what plays and when.

The component bar shows these as two tabs — Style and Motion — never as one flattened cross-product list, because an 8-structural × 47-eligible-motion container would be a 376-row list.

The parameters you would want to turn already exist — as derived values, not knobs. §7.7 lists them all: motion.duration-scale, motion.easing-set, motion.transition-presets, motion.stagger-policy, motion.distance-tokens. Every one is marked derived, meaning computed from the chosen direction. motion.distance-tokens is explicitly "bound to the spacing scale, never arbitrary translateY values."

And a deterministic generator already exists. §14.1 specifies variants.ts — reads the direction's tokens, emits parameterised component markup, no model call, instant. It also supplies "more like this": 5 deterministic neighbours of a variant you already approved.

The conflict your ask creates

This is the part that needs your decision rather than my judgement. D1's rule is that derived values are computed from the direction and never picked independently, and goal G3 states the design system is "coherent by construction" for exactly that reason. §7.7 extends that rule into motion by design — the note on motion.distance-tokens says so in as many words.

Exposing duration, easing, distance and stagger as knobs you turn is precisely the thing D1 forbids for every other derived value. It is not impossible — it is a deliberate exception, and it needs to be recorded as one rather than slipped in.

There is also a smaller tension with D4's "motion is not a separate parallel subsystem." A parameter engine with its own authoring surface is arguably that subsystem. Whether it counts as one is a judgement call about wording, and yours to make.

The question I need answered

Three shapes, increasing in cost and in distance from D1:

  • A bounded knob set — the direction still computes the defaults, and you nudge within a range it allows. D1 survives, because the direction still owns the ceiling and floor.
  • A free parameter surface — duration, easing curve, distance, delay, stagger, all directly editable. Fastest to feel powerful, and a stated exception to D1.
  • A compositional engine — you build an animation from primitives (what moves, from where, on what trigger, in what order) rather than tuning a preset. The biggest build, and the only one that genuinely deserves the word "engine."
